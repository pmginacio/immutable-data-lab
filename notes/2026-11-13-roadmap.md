# Roadmap

What is open in inlay on 2026-11-13, and what comes next.
Most items come from the follow-ups in `2026-11-10-design-v1.md`, the sales example note, and the discussions of the last days.
Nothing here is scheduled except "Next".

## Next

1. An immutable, append-only db, as an experiment next to inlay.
   See `2026-11-13-immutable-db.md`.
2. A version of that db that stores facts (datoms), also an experiment.
   See `2026-11-13-immutable-db.md`.

## Done

- A default db file: `open(entities, *, path=".inlay.db")`, with the same `path` keyword on `migrate` and `rename`.
  The file is in the current directory, as for any relative path, and the docs say so.
  A fixed place in the user's home was not chosen, because it couples unrelated programs.

## Features

- Optional fields (`X | None`). The sales example note ranks it first, as the most common need with real data.
- Enums.
- Composite keys. Today the parts are packed into the string key.
- Cascading deletes, probably opt-in for each `Ref`.
- Reverse relations, possibly in an explicit form such as "customers whose key is among the `customer` of these orders", so that no names are generated on the class.
- More functions, such as `hour` and the weekday of a datetime, and a way to start a business day at 6:00 with date arithmetic or an offset. A function takes one argument for now.
- Conditions on groups (`HAVING`), and several aggregates in one query, such as a `summary` with the count, sum, minimum and maximum.
- A `migrate` that tracks which migrations have run, and one that changes several classes in one step.

## Defects and small gaps

- `open` takes the write lock every time, so several processes opening a new file at once can fail.
  Reading the schema first, and taking the lock only to create tables, would fix it.
- Subclassing an `@entity` class raised a bare `KeyError: 'id'` when it was tested.
  It should be a clear `TypeError`.
- A `NaN` float or a wrongly typed value raises a raw `sqlite3.IntegrityError` instead of a `StoreError`.
- Passing the same key or record twice to `delete` or `remove` raises `Missing`.
- `startswith` cannot use an index. It could compile to a range.
- `ORDER BY` inside aggregates could be dropped when there is no slice.

## Design questions

- Whether typing `Order.total` as its value type pays off.
  The alternatives are a `Queryable[int]` annotation, a lambda that receives a recording proxy, and a separate field class.
  The complexity review found the duality costs about 50 lines, and reading a field on an instance is about 13 times slower than on a plain dataclass.
- Not passing entities to `open`: set a class up the first time `db[T]` uses it.
  It would also remove `other_entities` from `migrate`.
- Whether `del db[Cls]` is still needed, now that `migrate` drops the old table.
- Whether `open` should raise when it is about to create a table and an unclaimed table has the same columns, which catches a forgotten rename.
- Sharing a `Db` between threads, with one connection for each thread inside.
  The iteration guard is part of that decision: reading all rows in `__iter__` would remove it, at a cost in memory.
- Keeping or deleting `py.typed`.

## Performance

- A benchmark against raw `sqlite3`: bulk insert, load, a filter through a relation, many `.get()` calls, and a count.
- `list(view)` runs an extra `COUNT(*)`.
- Conditions on the same path could share one subquery, and `Order.customer.id` could use the `customer` column directly.

## Housekeeping

- Share the write path in `db.py`: `remove` repeats `_write`, and `delete` repeats the rowcount check.
- Remove duplicate tests.
- `.gitignore` does not cover real SAF-T files.
- A few doc fixes from the review of 2026-11-11.
- The threads and performance discussion is not written down.

## Out of scope

- An immutable db with history inside `inlay` itself: item 2 is an experiment first.
- Async, and other databases.
