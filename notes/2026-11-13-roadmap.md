# Roadmap

What is open in inlay on 2026-11-13, and what comes next.
Most items come from the follow-ups in `2026-11-10-design-v1.md`, the sales example note, and the discussions of the last days.
Nothing here is scheduled except "Next".

## Next

Nothing chosen yet.

## Paused

- The history db, paused on 2026-11-21 to work on inlay itself.
  Next would be designing which schema changes it allows, and how; see "Schema changes" in `2026-11-13-immutable-db.md`.
  It refuses optional fields and values read through a `Ref` until then.
- The datoms version, paused on 2026-11-21.
  It refuses optional fields and values read through a `Ref`.
  A current table and snapshot tables are done, so reads of the present no longer grow with history; see "A current table" in `2026-11-13-immutable-db.md`.
  Filters still build every record of the class; an index on the current table with step B's narrowing would be the next step.

## Done

- Enums, on 2026-11-22: a `StrEnum` or an `IntEnum` field is stored as its value and read back as a member; a stored value that is no member raises.
  The column is that of a `str` or an `int`, so a field that becomes an enum keeps its table and its hashed keys.
- Queries without a db, on 2026-11-22: `query(Order)` builds a query, a tree of plain data, and `db[q]` runs it.
  `Query` replaced `RecordView`: it holds an optional db only to run on, so `db[Order].filter(...)` still runs.
  Groups became a query too: filtered, sorted and sliced by `value` and by their keys as grouped by, and still a mapping when bound.
  So a group can be defined at module level and be a projection field, such as an ad's first sighting.
  `q[0]` as a query of one record, `LIMIT 1`, can come later the same way.
- Keys from the values, on 2026-11-22: `hashed()` makes the key the SHA-256 of the other fields, for values stored once however many records point to them.
  Records read back are restored field by field, without `__init__`, so a stored key is kept and a `__post_init__` runs only when a record is built.
  Changing a hashed class changes every key, so its referrers must be migrated with it, which needs the `migrate` of several classes below.
- Values of groups in queries, on 2026-11-22: `aggregate_by` gives a `Grouped`, a mapping read again on every read, and `totals[Order.customer]` gives each record the value of its own group.
  It compiles to a subquery on the grouped query; a key with no records gives `None`.
  It came from the HouseBargain app, which needs the newest snapshot of each listing.
- Projections, on 2026-11-22: `@projection(Root)` classes read with `view.project(cls)`, compiled as a subquery; see `2026-11-21-projections.md`.
- `db.migrate(fn, old, new)` and `db.rename(old_name, new)` on the db, on 2026-11-21, replacing `inlay.migrate` and `inlay.rename`; see "Migrate on the db" in `2026-11-13-migrations.md`.
  It changes one table and keeps its name, so a new table name or a key change while other tables point to it is refused.
- Values read through a `Ref`, such as `Order.customer.city`, as sort keys, group keys and aggregated values, on 2026-11-21.
  They compile to correlated subqueries; filters through a `Ref` keep the `IN` form.

- Optional fields, on 2026-11-21: `X | None`, and `Ref[T, str | None]` for references.
  `==` and `!=` compile to SQLite's `IS` and `IS NOT`, `negate` counts an unknown result as false, and `one_of` can hold `None`, so conditions keep Python's meaning.
  `Ref[T] | None` is refused: it is no descriptor, so type checkers would flag every record built with it and every path through it.

- `open(path)` without a list of classes, in inlay and the history db, on 2026-11-21; see `2026-11-21-open-without-classes.md`.
  `db.register(*classes)` creates tables and raises if one exists; `Cls in db` and `del db[Cls]` complete the mapping.
  Reading or writing a class with no table raises `KeyError`; a class with a table is checked on its first use, and its indexes follow the class.
  `migrate` lost `other_entities`. The datoms version still takes its classes in `open`.

- A benchmark of the history db against inlay, `benchmarks/history.py`, with reads at past transactions and the declared indexes in both orders.
  The results are in "Benchmark" in `2026-11-13-immutable-db.md`; `(tx_to, field)` stays.

- The history db, as an experiment: `inlay.history`, one table of versions per class, and `db.as_of(tx | datetime)`.
  See `2026-11-13-immutable-db.md`.
  Small gap: an update with an identical record still writes a version.

- A default db file: `open(entities, *, path=".inlay.db")`, with the same `path` keyword on `migrate` and `rename`.
  The file is in the current directory, as for any relative path, and the docs say so.
  A fixed place in the user's home was not chosen, because it couples unrelated programs.

## Features

The first real use, HouseBargain, added several of these; see `2026-11-22-housebargain-findings.md` for the evidence.

- A key that is also a `Ref`, for one-to-one records that extend another one, such as the user's marks on a listing.
- Classes nested in a class, stored as columns of the same table, for fields that belong together but are not shared.
- `dict` fields stored as JSON.
- Composite keys.
  Today the parts are packed into the string key.
- Cascading deletes, probably opt-in for each `Ref`.
- Reverse relations, possibly in an explicit form such as "customers whose key is among the `customer` of these orders", so that no names are generated on the class.
- More functions, such as `hour` and the weekday of a datetime, and a way to start a business day at 6:00 with date arithmetic or an offset.
  A function takes one argument for now.
- Several aggregates in one query, such as a `summary` with the count, sum, minimum and maximum.
  Groups can already be filtered, sorted and sliced by their one value, as in the ten most frequent kinds.
- Values of a record's place in its sorted group, such as its position or the previous record's value, for the first N of each group and for price drops.
  SQL has them as window functions; a `group_by(key)` that returns the groups, with `aggregate(func, value)` replacing `aggregate_by`, was discussed as the shape.
  The first of each group, such as HouseBargain's representative ad for each property, was weighed on 2026-11-22 and not added.
  A method like `first_by` would be a word no Python user knows, and the common way works: keep the records whose value equals their group's minimum, with a second group on the key to break ties.
  HouseBargain does that with two group values and a tie-break.
- Conditions as sort keys, sorted like bools, so a mixed order reads like Python's `key=lambda a: (not a.listed, a.price)` instead of needing a direction for each key.
- A `migrate` that tracks which migrations have run, and one that changes several classes in one step, which a key change of a table that others point to needs.
- Values read through a `Ref` as joins: grouping by one runs its subquery twice, and sorting by one and keeping the first N sorts the whole table.
  A `LEFT JOIN` was about twice as fast for the grouping, and 15 times for the first ten.
- Automatic migrations for changes that only add to a class, such as a new field, done on the class's first use as the declared indexes will be.
  A new field needs a value for the stored records: a new optional field can start as NULL, and SQLite's `ALTER TABLE ADD COLUMN` also takes a constant default.
  Changes that remove or change fields keep needing `migrate`, since they change stored data.
- A separate library that generates a web API from chosen classes, the way PostgREST does for Postgres tables and views.
  Entities would be readable and writable, projections read-only, with filters, sorting and paging in the query string, and `PATCH` limited to the fields the app lists as changeable.
  An app would mount it next to its own routes for what no query expresses: values computed in Python, actions such as starting a job, and writes that keep a rule across several records.
  inlay would need a small public API to describe a class (its fields, key, whether the key is hashed, its `Ref`s and their classes), and a documented way to use a db from the threads of a web server.
- Set operations between queries of one class, `a | b`, `a & b` and `a - b`, for what conditions cannot say, such as the ten cheapest and the favorites.
  SQLite's `UNION`, `INTERSECT` and `EXCEPT` do it.
- Queries saved and sent as data, such as JSON, for saved searches, the criteria of a HouseBargain sweep, and the web API above, where a client would send a query instead of using one endpoint for each filter.
- Queries equal when built the same way, leaving out the db they hold, so a test can check what a function builds without running it, and a query can key a cache.
  The tree is already frozen dataclasses; `Query` and `Grouped` are `eq=False`.
- A way to see a query's SQL, and SQLite's plan for it, to check that an index is used, without the internal `select_sql`.
- The page after a record, `q.after(last)`, filtering from the last record's sort key instead of skipping rows with a slice, which SQLite reads and discards.

## Defects and small gaps

- A condition on groups through a `Ref` works only when the `Ref` itself is a key: a group keyed by `Order.customer.city` cannot be filtered with `Order.customer.city == "Lisbon"`, which builds an `IN` on `Order.customer`.

- `x in view` is `False` for anything that is not a record of the class, so passing a key by mistake is never caught.
  It should raise a `TypeError`.
- The history db's `open` takes the write lock every time, to create its table of transactions, so several processes opening a new file at once can fail.
  inlay's `open` no longer writes; checking for the table first, and taking the lock only to create it, would fix the history db's.
- Subclassing an `@entity` class raised a bare `KeyError: 'id'` when it was tested.
  It should be a clear `TypeError`.
- A `NaN` float or a wrongly typed value raises a raw `sqlite3.IntegrityError` instead of a `StoreError`.
  The datoms version stores every value in one column of any type, so it does not refuse a wrongly typed value at all.
  Checking types in Python before writing would fix both.
- Type checkers flag `= None` as the default of a `Ref[T, str | None]` field, since the declared type is the descriptor.
- Passing the same key or record twice to `delete` or `remove` raises `Missing`.
- `startswith` cannot use an index.
  It could compile to a range.
- `ORDER BY` inside aggregates could be dropped when there is no slice.

## Design questions

- After the system clock goes back, the history db keeps transaction times from going back too, so `as_of(datetime.now(UTC))` can miss transactions already committed until the clock catches up.
  `as_of(db.tx)` is always right.
- The history db imports `inlay.db` only for the error classes; they could live in their own `inlay/errors.py` that both import.
- Whether typing `Order.total` as its value type pays off.
  The alternatives are a `Queryable[int]` annotation, a lambda that receives a recording proxy, and a separate field class.
  The complexity review found the duality costs about 50 lines, and reading a field on an instance is about 13 times slower than on a plain dataclass.
  Type checkers flag ordering comparisons on optional fields, such as `Order.discount > 5`, and this is accepted.
- Whether `register` should raise when it is about to create a table and an unclaimed table has the same columns, which catches a forgotten rename.
- Sharing a `Db` between threads, with one connection for each thread inside.
- Frozen views hold mutable members: the connection, and the iteration guard's `Counter`, which a loop changes and the db and its snapshots share.
  The views could hold the db and ask it to count a loop, so that only `Db` holds mutable state.
- Keeping or deleting `py.typed`.
- Running a `Function` or `Aggregate` as Python inside SQLite, with `sqlite3`'s `create_function` and `create_aggregate`, instead of writing it twice.
  The Python version would be the only one, so the two can no longer disagree, and a user's own function needs no SQL.
  inlay would convert the stored value with `from_sql` before the call and with `to_sql` after it, so a function never sees how dates are stored.
  Functions would be registered on the connection before a query that uses them, found by walking the query tree, each under a unique name.
  `sql=` would stay as an optional fast path, kept for `to_month`, `to_day` and `avg`.
  The costs: a measured 2 to 3 times slower for functions and about 7 times for aggregates, over 200,000 rows still under a quarter of a second; and a backend must be able to call Python, which DuckDB can and PostgreSQL cannot.
- Going one step further, lambdas in queries, with the same mechanism.
  On a field, `apply(lambda x: x.hour, Order.placed) >= 22` would be a one-off `Function` with no name or SQL, and work in filters, sorts and aggregates.
  On a whole record, `orders.filter(lambda o: o.total > o.discount * 2)` would have SQLite build each record and call the lambda.
  As with today's functions, an index cannot answer the lambda's part, but other conditions in the same filter still narrow the rows first.
  The record form also converts every field of each row it looks at.
  A lambda has no stable name, so each query would register it under a fresh one, and it could never back an expression index the way a `Function`'s SQL could.

## Performance

- A benchmark against raw `sqlite3`: bulk insert, load, a filter through a relation, many `.get()` calls, and a count.
- `list(view)` runs an extra `COUNT(*)`.
- Conditions on the same path could share one subquery, and `Order.customer.id` could use the `customer` column directly.
- History db updates and removals are about 10 times slower than inlay's, almost all of it in SQLite, ending old versions; see "Benchmark" in `2026-11-13-immutable-db.md`.
  Binding the transaction number once instead of a subquery in every row was tried and gained nothing.
  A 16 MB page cache instead of SQLite's 2 MB default makes an update round about 10% faster.
  Declared indexes made partial, on current versions only, make ending versions about 30% faster, but SQLite then stops using them for range filters and sorting, which become 5 to 90 times slower.
- The history db's `as_of(datetime)` walks back through the transactions from the newest, so an old time costs more: 27 ms before the first of a million transactions.
  An index on `at` and `ORDER BY at DESC, tx DESC LIMIT 1` make it a direct lookup, at one index entry per transaction.
