# Roadmap

What is open in inlay on 2026-11-13, and what comes next.
Most items come from the follow-ups in `2026-11-10-design-v1.md`, the sales example note, and the discussions of the last days.
Nothing here is scheduled except "Next".

## Next

1. The datoms version: a version of the history db that stores datoms, also an experiment.
   A current table and snapshot tables are done, so reads of the present no longer grow with history; see "A current table".
   Filters still build every record of the class; an index on the current table with step B's narrowing is next.
   See "The datoms version" in `2026-11-13-immutable-db.md`.
2. Design which schema changes the history db allows, and how.
   See "Schema changes" in `2026-11-13-immutable-db.md`.

## Done

- A benchmark of the history db against inlay, `benchmarks/history.py`, with reads at past transactions and the declared indexes in both orders.
  The results are in "Benchmark" in `2026-11-13-immutable-db.md`; `(tx_to, field)` stays.

- The history db, as an experiment: `inlay.history`, one table of versions per class, and `db.as_of(tx | datetime)`.
  See `2026-11-13-immutable-db.md`.
  Small gap: an update with an identical record still writes a version.

- A default db file: `open(entities, *, path=".inlay.db")`, with the same `path` keyword on `migrate` and `rename`.
  The file is in the current directory, as for any relative path, and the docs say so.
  A fixed place in the user's home was not chosen, because it couples unrelated programs.

## Features

- Optional fields (`X | None`).
  The sales example note ranks it first, as the most common need with real data.
- Enums.
- Composite keys.
  Today the parts are packed into the string key.
- Cascading deletes, probably opt-in for each `Ref`.
- Reverse relations, possibly in an explicit form such as "customers whose key is among the `customer` of these orders", so that no names are generated on the class.
- More functions, such as `hour` and the weekday of a datetime, and a way to start a business day at 6:00 with date arithmetic or an offset.
  A function takes one argument for now.
- Conditions on groups (`HAVING`), and several aggregates in one query, such as a `summary` with the count, sum, minimum and maximum.
  Also sorting groups by their aggregate and keeping the first N, such as the ten most frequent kinds, which `aggregate_by` cannot do today.
- Projections: a read-only class defined by expressions over one root class, read like a class, and `view.project(cls)`.
  Optional fields should come first, so that a path through a `Ref` can be empty.
  See `2026-11-21-projections.md`.
- A `migrate` that tracks which migrations have run, and one that changes several classes in one step.

## Defects and small gaps

- `open` takes the write lock every time, so several processes opening a new file at once can fail.
  Reading the schema first, and taking the lock only to create tables, would fix it.
- Subclassing an `@entity` class raised a bare `KeyError: 'id'` when it was tested.
  It should be a clear `TypeError`.
- A `NaN` float or a wrongly typed value raises a raw `sqlite3.IntegrityError` instead of a `StoreError`.
  The datoms version stores every value in one column of any type, so it does not refuse a wrongly typed value at all.
  Checking types in Python before writing would fix both.
- Passing the same key or record twice to `delete` or `remove` raises `Missing`.
- `startswith` cannot use an index.
  It could compile to a range.
- `ORDER BY` inside aggregates could be dropped when there is no slice.

## Design questions

- After the system clock goes back, the history db keeps transaction times from going back too, so `as_of(datetime.now(UTC))` can miss transactions already committed until the clock catches up.
  `as_of(db.tx)` is always right.
- The history db imports `inlay.db` only for the error classes; they could live in their own `inlay/errors.py` that both import.
- Whether typing `Order.total` as its value type pays off.
  The alternatives are a `Queryable[int]` annotation, a lambda that receives a recording proxy, and a separate field class.
  The complexity review found the duality costs about 50 lines, and reading a field on an instance is about 13 times slower than on a plain dataclass.
- Not passing entities to `open`: set a class up the first time `db[T]` uses it.
  It would also remove `other_entities` from `migrate`.
- Whether `del db[Cls]` is still needed, now that `migrate` drops the old table.
- Whether `open` should raise when it is about to create a table and an unclaimed table has the same columns, which catches a forgotten rename.
- Sharing a `Db` between threads, with one connection for each thread inside.
  The iteration guard is part of that decision: reading all rows in `__iter__` would remove it, at a cost in memory.
- Frozen views hold mutable members: the connection, and the iteration guard's `Counter`, which a loop changes and the db and its snapshots share.
  Removing the guard removes the `Counter`; keeping it, the views could hold the db and ask it to count a loop, so that only `Db` holds mutable state.
  Decide together with the guard.
- Keeping or deleting `py.typed`.
- Running a `Function` or `Aggregate` as Python inside SQLite, with `sqlite3`'s `create_function` and `create_aggregate`, instead of writing it twice.
  The Python version would be the only one, so the two can no longer disagree, and a user's own function needs no SQL.
  inlay would convert the stored value with `from_sql` before the call and with `to_sql` after it, so a function never sees how dates are stored.
  Functions would be registered on the connection before a query that uses them, found by walking the query tree, each under a unique name.
  `sql=` would stay as an optional fast path, kept for `to_month`, `to_day` and `avg`.
  The costs: a measured 2 to 3 times slower for functions and about 7 times for aggregates, over 200,000 rows still under a quarter of a second; and a backend must be able to call Python, which DuckDB can and PostgreSQL cannot.

## Performance

- A benchmark against raw `sqlite3`: bulk insert, load, a filter through a relation, many `.get()` calls, and a count.
- `list(view)` runs an extra `COUNT(*)`.
- Conditions on the same path could share one subquery, and `Order.customer.id` could use the `customer` column directly.
- History db updates and removals are about 10 times slower than inlay's, almost all of it in SQLite, ending old versions; see "Benchmark" in `2026-11-13-immutable-db.md`.
  Binding the transaction number once instead of a subquery in every row was tried and gained nothing.
  A 16 MB page cache instead of SQLite's 2 MB default makes an update round about 10% faster.
  Declared indexes made partial, on current versions only, make ending versions about 30% faster, but SQLite then stops using them for range filters and sorting, which become 5 to 90 times slower.
- The history db's `as_of(datetime)` walks back through the transactions from the newest, so an old time costs more: 27 ms before the first of a million transactions.
  An index on `at` and `ORDER BY at DESC, tx DESC LIMIT 1` make it a direct lookup, at one index entry per transaction.
