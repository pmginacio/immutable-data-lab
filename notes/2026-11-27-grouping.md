# Grouping

A discussion on 2026-11-27 about one form for grouping, aggregates and distinct values.
Nothing is decided; the options are kept here to revisit from the roadmap.

## Where it started

HouseBargain wanted the distinct municipalities the ads name, and wrote `named.aggregate_by(location.municipality, len)`, which counts ads per municipality and then reads only the keys.
inlay has no way to ask for distinct values.

A `DISTINCT` on rows would do nothing in inlay: every record and every projection carries the key, so rows are always distinct.
It only matters once some columns are chosen without the key, which is grouping.

## What inlay has today

Rows: `query(Order)` with `filter`, `sorted` and slicing, and `.project(P)` for another shape of the same rows.

Groups: `.aggregate_by(key, func, value)` gives a `Grouped`, a mapping from key to value, which can also be filtered, sorted and sliced.

Single values: `sum`, `min`, `max` and `len` on a query run right away and give one value.

## One general form

The three are one operation, as in SQL and in relational algebra's grouping operator:

- A key and an aggregate: the aggregate for each key, as `aggregate_by` does today.
- No key: the whole query is one group, so one value, as `SELECT sum(total) FROM orders` without a `GROUP BY`.
- A key and nothing else: the distinct keys, as `SELECT a, b FROM t GROUP BY a, b`.

A value without an aggregate means nothing and is an error.
Collecting the values of each group is an aggregate too, `list` or `set`, so it needs no special case.

With no key there is always exactly one group, even on an empty table: `sum` of nothing is 0 and `max` of nothing is None.
With a key, an empty table has no groups.
SQL has the same split, and the general form must keep it.

What it would gain:

- One idea instead of three.
- Single values that stay queries, so they can be used in other queries, as in `filter(Order.total > average)`, which inlay cannot do today.
- Distinct keys that are filtered, sorted and sliced like any group, and could be a subquery in `one_of`.

The name would change: "aggregate by" with no key is "aggregate", and with no aggregate it is "group by".
`group_by` reads right for all three.

## Aggregates as expressions

Today the function and its value are separate arguments: `aggregate_by(key, sum, Order.total)`.
If an aggregate were an expression, as `to_day(Order.at)` already is a value, the form becomes `group_by(key, expr)`:

- `group_by(Order.customer, Order.total.sum())`, the total of each customer.
- `group_by(Order.customer)`, the distinct customers.
- `group_by((), Order.total.sum())`, or no key at all, one value.
- `group_by(Order.customer, Order.id.count())`, the orders of each customer.

It opens arithmetic on aggregates, such as `Order.total.sum() / Order.id.count()` or `Order.total.max() - Order.total.min()`.

### Aggregates are methods of a value

Decided on 2026-11-27: `.sum()`, `.min()`, `.max()` and `.count()` on a value, and Python's built-ins are no longer taken.
With fields declared `Field[int]`, `Order.total` is an `Expr[int]` to type checkers, so its methods are checked and give an aggregate of the right type.

The built-ins were weighed and left out.
`len` must return an `int`, so a count needed a name of its own anyway.
`sum`, `min` and `max` can give an expression, by making a field iterable and yielding stand-ins that record `+`, `<` or `>`, but a field that pretends to be iterable lets `list(Order.total)` pass silently, and no documentation promises that CPython's `min` compares with `<` and `max` with `>`.

`count()` counts the rows where the value is not None, as SQL's `COUNT(x)`; the rows of a group are `Order.id.count()`, since a key is never None.
An aggregate of the user's, such as a `distinct_count`, cannot be a method, so it is called as a `Function` is, `distinct_count(Order.at)`; whether `avg` becomes a method too, so the common ones read alike, is open.

An aggregate must be refused in a condition on records, such as `filter(Order.total.sum() > 5)`, and allowed only on groups, as SQL's `HAVING` against `WHERE`.
inlay already refuses conditions on groups that belong on the records, so this is the same check the other way.

## Several values

A group often needs more than one value, such as the largest order and the most items of each customer.
Python allows no positional argument after a keyword one, so the key comes first: `group_by((k1, k2), Order.value.max(), Order.items.max())`.

What a group then gives is the open question.

1. Positional tuples: `(k1, k2)` maps to `(largest, most_items)`.
   It is closest to SQL, but the values have no names, so filtering and sorting by them goes by position, and `totals.value` no longer fits.
2. Named values: `group_by((k1, k2), largest=Order.value.max(), most_items=Order.items.max())`.
   Each group has named fields, as in `.filter(stats.largest > 100)` and `.sorted(key=stats.most_items)`.
   The names are declared nowhere a type checker or an editor can see.
3. A projection with aggregate fields:

   ```python
   @projection(Order)
   class CustomerStats:
       customer: Field[str] = Order.customer
       largest: Field[int] = Order.value.max()
       most_items: Field[int] = Order.items.max()

   db[Order].project(CustomerStats)
   ```

   As in SQL, the fields that are not aggregates are the grouping key.
   Grouping is then no separate method: a projection is a shape of the rows, and some shapes collapse them.
   A distinct is a projection with only key fields, and one value for the whole query one with only aggregate fields.
   It would replace `aggregate_by`, `Grouped` and its `.value`, and the aggregate methods on a query.
   Against it: an ad hoc question needs a class, and the key of such a projection is the grouping key, not the root's, which changes how projections take their key today.

## A result is a table with a key

The leaning after the discussion: 3 for shapes that are reused, and 2 for ad hoc questions, both the same mechanism.

A grouped result is a table whose key is the group key, unique in it as `id` is among orders.
So it works as any set of records in inlay does.
Its columns have names, also the keys, which are not always self-describing: grouping by `Order.customer.city` and `Order.store.city` gives two `city`.
`filter`, `sorted` and slicing keep the columns, and a projection of it must keep its key, as projections must today, so the key is never lost however many steps follow.
Read, it gives a mapping from key to row, as `db[Order]` gives records that `get` finds by key.
A key of several fields is a tuple in that mapping, as with `aggregate_by` today.

A result with one value gives rows too, as `Row(customer="ana", total=160)`: a bare value per key cannot be a collection of rows, which iterating would give without their keys.

### One shape for every query

A grouped result read as a mapping from key to row would not fit a query of records, which is read as a collection of records.
Two ways to make them one shape:

1. Every query is a lazy collection of rows, as a query is today: iterating gives rows, `get(key)` finds one, and `items()` gives `(key, row)` pairs, so `dict(q.items())` is the mapping when one is wanted.
   Loops stay short, `for order in orders`, and slicing reads naturally, `orders[:10]`.
   Against it: a group of one value loses today's `{customer: total}`, which becomes `{r.customer: r.total for r in totals}`, and lookup by key stays a method.
2. Every query is a lazy mapping from key to row.
   Records, projections and groups are one shape, and a group of one value can map to its value.
   `orders["o1"]` and `"o1" in orders` read as Python; today `in` takes a record, and a key quietly gives `False`, a defect on the roadmap.
   `keys()`, `values()` and `items()` come with it, and a mapping converts straight to JSON or a DataFrame.
   A set of records unique by their key is keyed by it already, and a mapping says so; a dict of objects keyed by their id is common in Python, as Django's `in_bulk` gives.
   Against it: `[]` does two jobs, a key and a slice, which no Python mapping does; looping over rows becomes `for order in orders.values()`, since a mapping iterates its keys; and a sorted or sliced result is an ordered mapping, which reads less plainly than rows in order.

Neither is clearly better: the mapping is one standard shape with lookup by key, the collection keeps loops and slices short.
Decided on 2026-11-27: the collection of rows, a set of records as today, for every query, grouped or not.

With it, `items()` on every query, records included, gives `(key, row)` pairs, so `dict(q.items())` is the mapping.
HouseBargain builds such a mapping to look records up by key, as in `{loc.id: loc for loc in db[Location]}`, which would become `dict(db[Location].items())`.
A mapping from one field to another, such as each ad's property from `AdProperty`, stays a comprehension.
`asdict` was weighed as the name and left out: `dataclasses.asdict(record)` already means a record's fields as a dict, and a query method of the same name would mean keys to records.

### Without a class

Keys are positional, a field or a tuple of them, and values are keyword arguments:

```python
stats = db[Order].group_by(Order.customer, largest=Order.value.max(), most_items=Order.items.max())
stats.filter(stats.largest > 100).sorted(key=stats.most_items)
dict(stats)  # {"ana": Row(customer="ana", largest=120, most_items=4), ...}
by_place = db[Order].group_by({"from": Order.customer.city, "at": Order.store.city}, total=Order.total.sum())
```

A key column is named after its last field, and a clash raises; a dict names keys explicitly.
A single positional value is named `value`, so `group_by(Order.customer, Order.total.sum())` reads as today's `aggregate_by`, `totals.value` included.
Telling keys from values by whether an expression holds an aggregate, as SQL does, was weighed and left out: the split would not show in the call, as an implicit "and" in `filter(a, b)` did not.

A row is a named tuple, built for each query from the column names.
SQLAlchemy's `Row` and Django's `values_list(named=True)` settled on the same; `row.largest`, `row[0]` and unpacking all work.
`sqlite3.Row` was weighed: it has no attribute access, holds the stored values, such as dates as text and bools as 1, and would tie the API to SQLite.

Each column's type comes from its expression, through `result_type`, as projections and `aggregate_by` already work it out, and `from_sql` converts it before the row is built.
Aggregates need a case there: `count` gives an `int`, `avg` a `float`, and `sum`, `min` and `max` the type of what they aggregate.

## What it would simplify

`Grouped`, about 85 lines, is a second kind of query with its own `filter`, `sorted`, slicing, `.value` and lookups.
A grouped result would be an ordinary query whose rows are named tuples or projections, so those exist once, and the translation in `group_condition` and `group_column` goes.
`aggregate_by`, `sum`, `min` and `max` on a query, about 65 lines with their overloads, become one-group `group_by`s.

Added: aggregate nodes and their types, the checks below, building rows, the key rule for projections, and the stand-ins for the built-ins if they are kept.
The lines may come out even; the gain is one kind of query, lazy single values, several aggregates and arithmetic on them.
A trial that replaces `aggregate_by` and `Grouped` and keeps the tests' cases would measure it.

## Corner cases

An aggregate expression is valid in some places and wrong in others, which no expression is today.
All the checks walk the expression tree for aggregate nodes, as inlay already walks conditions.

Places to refuse an aggregate:

- An entity field, such as `total: Field[int] = Order.x.sum()`, when the class is defined.
- A projection that keeps the root's key: with `id` and `n: Field[int] = Order.id.count()`, every group is one order and the count is always 1.
  A projection either keeps the root's key and has no aggregates, or has aggregates and its plain fields are the key.
- A condition or sort key on records.
  `filter(Order.total > Order.total.avg())` reads as "the orders above average", but over which orders, before or after the other filters, is not said.
  The message names the explicit form: the average as its own one-group query, used in the filter.
  On grouped results the same conditions are allowed, as SQL's `HAVING`.
- A key, an aggregate inside another, such as `Order.total.max().sum()`, and a field outside an aggregate that is not a key or built only from keys, such as `Order.total.sum() / Order.discount`.
  SQLite takes an arbitrary row for such a field, which is worse than an error.

Empty groups and `None`:

- With no key there is always one group, also on an empty table, so `min` and `max` there give `T | None`.
  With a key, every group has at least one row.
- `count()` skips the `None`s of its value, as SQL's `COUNT(x)`; the rows are `Order.id.count()`.

Names of ad hoc rows:

- Two keys of the same name, or a key and a value of the same name, raise.
- Named tuples refuse names that start with `_` and keywords, so inlay checks first and says so.

Lookups from another query:

- `totals[Order.customer]` gives each order its customer's total today.
  With several values a lookup must name the column, perhaps `stats.largest[Order.customer]`.

## Aggregates in a projection

Decided on 2026-11-28.

### Words

A `Ref` is a foreign key, and the only relation inlay stores.
From the record that holds it, it is **to-one**: `Order.customer` reaches at most one customer.
Read the other way it is **to-many**: a customer has any number of orders, its back-references, and no field holds them, since a field holds one value.
One-to-many is the `Ref` read backwards, many-to-many a class of two `Ref`s such as `OrderLine`, and one-to-one a `Ref` that would also be unique, which inlay does not enforce yet.

The kinds of expression, each belonging to one class of record:

- a **value**, one per record: `Order.amount`, `Order.customer.city`, `Order.amount * 2`, `to_day(Order.placed)`;
- a **condition**, true or false per record: `Order.paid != None`;
- an **aggregate**, one value of a record computed over its back-references: `Order.amount.sum()` in a projection of `Customer` belongs to `Customer`;
- a **query**, a set of records that is read: `query(Order).filter(...)`, `db[Order]`.

### The rule

`.` follows a `Ref` the narrowing way, to one record, so a projection reads values through references freely.
The widening way reaches many records, so a projection can only take it through an aggregate, which gives one scalar per record.

An aggregate has no meaning on its own: it aggregates over its scope, given by where it is placed.
In a projection of `Customer`, the scope of an aggregate of `Order` is each customer's orders, through the one `Ref` from `Order` to `Customer`.
Inside `group_by`, the scope is each group.
Anywhere else it is refused.

The `Ref` is inferred when the aggregated class has exactly one `Ref` to the projected class and is not that class itself; otherwise it is named, as the first argument.
`filter=` removes records before they are aggregated, as `query(...).filter` and Python's `filter` do: the same word for the same operation, applied to the set the aggregate already has.
`count` and `sum` of no records give 0, as `len([])` and `sum([])` do; `min`, `max` and `avg` give None.
`.sum()`, `.min()`, `.max()`, `.count()` and `.avg()` are the common aggregates, and `.agg(f)` takes any `Aggregate`, a user's own included.
An aggregate is of a value, computed per record before aggregating, and arithmetic on aggregates happens after; one function per step covers every expression of aggregates, since each depends only on the set aggregated.

```python
@projection(Customer)
class CustomerRow:
    id: Field[str]
    name: Field[str]                                                        # its own field
    referrer: Field[str | None] = Customer.referred_by.name                 # forward, through a reference
    total: Field[int] = Order.amount.sum()                                  # Order.customer is inferred; 0 with no orders
    orders: Field[int] = Order.id.count()
    last_order: Field[datetime | None] = Order.placed.max()                 # None with no orders
    avg_spend: Field[float | None] = Order.amount.sum() / Order.id.count()  # arithmetic on aggregates
    paid: Field[int] = Order.amount.sum(filter=Order.paid != None)          # the paid orders only
    days_ordered: Field[int] = to_day(Order.placed).agg(distinct_count)     # a user's own aggregate
    items: Field[int] = OrderLine.qty.sum(OrderLine.order).sum(Order.customer)  # two hops, the references named
    referrals: Field[int] = Customer.id.count(Customer.referred_by)        # a reference to its own class is named


@projection(Order)
class OrderRow:
    id: Field[str]
    value: Field[int] = (OrderLine.qty * OrderLine.unit_price).sum()        # computed per line, then summed


@projection(Address)
class AddressRow:
    id: Field[str]
    billed: Field[int] = Order.id.count(Order.billing)                      # two references to Address, so named
    shipped: Field[int] = Order.id.count(Order.shipping)
```

Two hops may also be written `OrderLine.qty.sum().sum()`, each step inferred, but naming the references reads better.

### Refused when the class is defined

- An aggregate outside a projection or `group_by`, such as `Order.amount.sum()` at module level.
- An aggregate whose class has no `Ref` to the projected class, or two, or is the projected class, without the `Ref` named.
- A named `Ref` that does not point at the projected class.
- A `filter=` condition of another class than the one aggregated.
- A declared type that does not match, such as `avg_spend: Field[float]`, which needs `| None`.

### Weighed and left out

- Today's lookup, `query(Order).aggregate_by(Order.customer, sum, Order.amount)[Customer.id]`: any group and any match, which is more than makes sense, and the join written twice.
- `agg(expression, by=...)` with several aggregates inside one expression: it needs a check that every field is inside an aggregate, and gives nothing that arithmetic on single aggregates does not, since each depends only on the set aggregated.
- A starting point naming the back-reference, `children(Order.customer)` or `many(Order, Order.customer)`: a special entry point; and fields read on it cannot be typed.
- The match written as a condition, `query(Order).filter(Order.customer == Customer.id)`: a join disguised as a filter.
- A filtered value, `Order.amount.where(cond)`, `None` where the condition fails: it keeps every record, so outside an aggregate it is a different operation from `filter`.
- `Order.filter(...)` on the class: type checkers cannot see methods a decorator adds, and a base class would make them clash with field names.

### Compiling

Each aggregate is a correlated scalar subquery on the `Ref`'s column, which is always indexed: `(SELECT COALESCE(SUM(amount), 0) FROM "order" WHERE customer = customer.id AND paid IS NOT NULL)`.
The aggregates along the same `Ref` and filter can later share one grouped `LEFT JOIN`, as the values read through the same reference path can share one join; neither changes results.
