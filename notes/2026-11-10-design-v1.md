# inlay: a set-like store for flat immutable classes

Design notes from 2026-11-10, before any code.
The goal is to define flat, frozen classes in the app and read and write them without seeing SQL.
SQLite is the only backend.

## Example

```python
from dataclasses import replace
import inlay
from inlay import entity, key, Ref

@entity(indexes=[("city",)])
class Customer:
    id: str = key()
    name: str
    city: str

@entity(indexes=[("customer",), ("total",)])
class Order:
    id: str = key()
    customer: Ref[Customer]
    total: int

with inlay.open("shop.db", [Customer, Order]) as db:
    ana = Customer(name="Ana", city="Lisbon")
    with db.transaction():
        db.add(ana, Order(customer=ana.id, total=120))

    big = db[Order].filter(Order.total > 100, Order.customer.city == "Lisbon")
    for o in big.sorted(key=Order.total, reverse=True)[:10]:
        print(o)

    o = db[Order].get(some_id)
    db.update(replace(o, total=150))
    db[Order].clear(Order.total == 0)
```

## Principles

- The db is a set of whole records per class, where no two records share a key.
  Reads return whole records, never single fields.
- Records are frozen.
  The db is mutable: it stores new versions of records and drops old ones.
- The API copies Python built-ins (`set`, `dict`, `sorted`, slicing) where it can.
- Filtering, sorting, limits, deleting by condition, simple aggregates (`len`, `sum`, `min`, `max`) and aggregates by key run in SQLite.
  Everything else (combining classes) is plain Python over the records.
- Only `inlay.open` and the `db` object touch SQLite.
  Building conditions and compiling them to SQL are pure functions.

## Defining classes

An entity is a class marked with `@entity`; its instances are called records.

`@entity(table=..., indexes=[...])` applies `dataclass(frozen=True, slots=True, kw_only=True)` and stores the metadata the db needs.
Both arguments are optional, and plain `@entity` works too.

- `table` defaults to the class name in snake_case: `Customer` is `customer`, `OrderLine` is `order_line`.
  It stays singular, because plural rules (`Category`, `Person`) are easy to get wrong.
  Renaming a class renames its table, and `inlay.open` would then create a new, empty table without any warning.
  To rename a class that already has data, pin the old name with `table=`.
- Table and column names are always quoted in SQL, since names like `order` are SQL keywords.
  The SQL examples in this note leave quotes out where they are not needed.
- The key is the one field declared with `= key()` (see ids).
  Every class has exactly one; classes without a key are not supported.
- `indexes` is a list of tuples of field names.
  Each tuple is one index, so `("city", "name")` is a composite index.
  Every index is declared here, including ones on `Ref` fields.
  Nothing is indexed implicitly, except the key.
- The decorator checks, when the class is defined:
  - there is exactly one key,
  - every field type is supported (see field types),
  - no field is named `startswith`, `endswith` or `_apply`: field references use those names for methods, so `Order.customer.startswith` could never reach such a field,
  - every index field exists,
  - every `Ref` field is the first field of some index.

The last check exists because SQLite does not index foreign key columns on its own.
Without an index, filters through the relation and the check SQLite runs when a referenced record is deleted both scan the whole table.
The error names the fix: `Order.customer is a Ref but no index starts with it; add ("customer",) to indexes`.

Each field gets a descriptor that wraps the slot.
Read on a record, it returns the value.
Read on the class, it returns an `Expr` for building conditions.
An `Expr` holds the `Ref` fields followed from the filtered class, and the value computed on the record they reach: a field, or arithmetic and date transforms of fields.
`Order.total` follows no relation, and `Order.customer.city` follows one.
Reading an attribute of an `Expr` that is a `Ref` field follows it, so `Order.customer` is both a field and the way to its customer's fields.

### Field types

| Python | SQLite column |
|---|---|
| `int` | `INTEGER` |
| `float` | `REAL` |
| `str` | `TEXT` |
| `bytes` | `BLOB` |
| `bool` | `INTEGER` (0 or 1) |
| `datetime` | `TEXT` (ISO 8601) |
| `date` | `TEXT` (ISO 8601) |
| `Ref[T]` | same as the key of `T` |

SQLite compares, sorts and aggregates `datetime` and `date` values as text, which follows time order only when the text has one form.
So an aware `datetime` is stored in UTC: it reads back in UTC, and still equals the value that was written, because Python compares aware datetimes by moment.
A naive `datetime` is stored as it is.
Keep each field all naive or all aware: Python refuses to compare the two, and SQLite would compare their text without an error.

All columns are `NOT NULL`.
`X | None` and `Enum` are left out of v1.
Any other type is an error when the class is defined.

Tables are `STRICT`, so SQLite checks types too.

### Ids

The key is set when the record is created, before it exists in the db.

```python
@entity
class Customer:
    id: str = key()
    name: str
    city: str

Customer(name="Ana", city="Lisbon")              # id generated
Customer(name="Bob", city="Porto", id="c1")      # id given
replace(ana, city="Porto")                       # keeps ana's id
```

All fields are keyword-only.
`@entity` applies `dataclass(kw_only=True)` and is marked with `dataclass_transform(kw_only_default=True)`, so type checkers agree.

- Keyword-only fields have no rule about fields with defaults coming first, so the key can stay first.
- Calls with names are clearer for wide records, and adding a field never shifts other arguments.
- `key()` returns `field(default_factory=...)`, and the factory returns `str(uuid.uuid7())`.
  Type checkers see it as a plain default, so they know the key is optional.
  `key` is not registered as a field specifier: type checkers would then only see a default passed in the call itself, and they ignore the ones inside `key()`.
- Rows loaded from the db pass the key, so loading never generates one.
- UUIDv7 starts with a timestamp, so new keys land at the end of the index instead of all over it.
- Keys are `str` in v1.
  `key()` could later take its own `default_factory`, for example for integer keys the app chooses.

Why not SQLite autoincrement:

- The record would have no key until it is inserted, so the key field would need to be optional.
- `add` would have to return new copies with the keys filled in.
- You could not build a customer and its orders in one `add`, because the orders need the customer's key first.

### Relations

`customer: Ref[Customer]` declares a reference to `Customer`.

`Ref` holds no data and is never instantiated.
It is a descriptor class that exists for type checkers:

```python
class Ref[T]:
    @overload
    def __get__(self, obj: None, owner: type) -> type[T]: ...     # Order.customer
    @overload
    def __get__(self, obj: object, owner: type) -> str: ...       # o.customer
    def __set__(self, obj: object, value: str) -> None: ...       # constructor argument type
```

- Type checkers see `o.customer` as a `str`, and `Order.customer` as `type[Customer]`, so `Order.customer.city` is a `str`.
- Typos like `Order.customer.nmae` and passing a non-`str` to the constructor are flagged.
- Checked with mypy and pyright.
- At runtime, `@entity` reads the type hint: `get_origin(hint) is Ref`, and `get_args(hint)` is `(Customer,)`.
  It then replaces the field with its own descriptor, like every other field.
- A class can refer to itself, or to a class defined later in the module: `parent: Ref[Category]`.
  Since Python 3.14, annotations are only evaluated when asked for, so no quotes are needed.
  `@entity` reads annotations with `annotationlib.get_annotations(cls, format=Format.FORWARDREF)`, which leaves names that do not exist yet as forward references instead of failing.
  Those are resolved in `inlay.open`, once all entities are known.

Then:

- The column is `customer`, with a foreign key to `customer(id)`.
- On a record, `order.customer` is the customer's key.
  Following it is an explicit lookup: `db[Customer].get(order.customer)`.
- On the class, `Order.customer` is a path to the related customer, and `Order.customer.city` is a field reached through it.

Every field is stored in a column with the same name, relations included, so there is no second set of names to learn.

Foreign keys are `DEFERRABLE INITIALLY DEFERRED`: SQLite checks them when the transaction commits, not on each row.
So the order of writes inside a call or a transaction never matters, and a record can refer to itself or to another record written in the same call.
A write that would leave a `Ref` pointing to nothing raises `BrokenRef` at commit: at the end of the call, or at the end of the `transaction()` block it is in.
That covers both adding a record whose target is not stored and deleting a record something still refers to.
There is no cascade in v1.

## Conditions

Conditions are frozen trees built from fields and values.
The base class is `Condition`.

| Python | Meaning |
|---|---|
| `Order.total > 100` | comparison: `==` `!=` `<` `<=` `>` `>=` |
| `Order.total > Order.discount` | comparing two columns of the same record |
| `Customer.name.startswith("A")` | also `endswith`, both case-sensitive |
| `contains(Customer.name, "x")` | substring, case-sensitive |
| `one_of(Order.status, ("new", "paid"))` | `IN` |
| `Order.customer == ana.id` | relation by key, a comparison on the `customer` column |
| `Order.customer.city == "Lisbon"` | condition on the related record |
| `Order.total * 100 > 5000` | arithmetic on numbers: `+` `-` `*` `/`, with `/` always a real division as in Python |
| `to_month(Order.placed) == date(2026, 1, 1)` | the first day of the month of a `date` or `datetime`; `to_day` gives its date |
| `any_of(a, b)`, `a \| b` | or |
| `all_of(a, b)`, `a & b` | and |
| `negate(a)` | not |
| `none_of(a, b)` | neither: not (a or b) |

Several conditions passed to `filter` are combined with and.

`&` and `|` bind tighter than comparisons in Python, so they need parentheses: `(Order.total > 1) | (Order.total == 0)`.
Without them, `Order.total > 1 | Order.total == 0` is read as `Order.total > (1 | Order.total) == 0` and fails with a `TypeError` on `1 | Order.total`.

A type checker sees `Customer.name` as a `str` and `Order.total > 100` as a `bool`.
So only methods that `str` already has (`startswith`, `endswith`) can be methods.
`contains` and `one_of` are functions instead.
`~` is left out because type checkers see `~` on a `bool` as an `int`, and in strict mode flag it as deprecated (it becomes an error in Python 3.16).

`all_of`, `any_of` and `none_of` play the role of the built-ins `all` and `any`, which cannot be used: they call `bool()` on each item and return a plain `bool`.
They take conditions as separate arguments, and with none they match the built-ins: `all_of()` and `none_of()` match everything, `any_of()` matches nothing.

Python forces `and`, `or`, `not`, `in`, `is` and chained comparisons like `1 < x < 5` to a real bool.
`Condition.__bool__` raises a `TypeError` that names the right replacement, so these mistakes fail loudly.

A misspelled field (`Order.totl`, `Order.customer.nmae`) raises `AttributeError` when the condition is built.
Comparing fields of two different records (`Order.total > Customer.age`) raises `ValueError` when the condition is built too.
`filter` and `clear` check their conditions right away: a field that cannot be reached from the collection's class (`db[Customer].filter(Order.total > 1)`) or a plain `bool` raises there, not when the view is read.
`sorted`, `sum`, `min` and `max` check right away too that their value is computed from fields of the collection's class itself, and `sum` that it is a number.

Wherever a field is expected, a relation stands for its `Ref` field: `one_of(Order.customer, keys)`, `sorted(key=Order.customer)` and `min(Order.customer)` use the `customer` column.

`to_month` and `to_day` are the same functions on both sides: given a `date` or `datetime` they compute in Python, and given a field such as `Order.placed` they build a node that SQLite computes.
So a report can use the same function in a loop over records and in a filter.
Arithmetic needs numbers and the transforms need a `date`; anything else raises `TypeError` when the value is built.
Aware datetimes are stored in UTC, so the transforms see them in UTC, as do records read back.

### The tree

Two layers build and hold a condition:

- The builder is what users write: `Expr` (from `Order.total`), its operators, `contains` and `one_of`, in `conditions.py`.
  It carries the typing tricks, and it only ever returns tree nodes.
- The tree is plain frozen data in `nodes.py`, with normal equality and no operators that build anything.
  Code that checks, inspects or compiles conditions only sees the tree.
  `result_type` holds every type rule, so a badly typed value raises as soon as the builder makes it.

The functions in `functions.py` depend on neither.
Called on a plain value, a `Function` computes in Python; called on anything else that has an `_apply` method (the `Applicable` protocol), it hands itself to that method.
`Expr._apply` builds the `Call`, the same way its operators build a `BinOp`.
So the imports go one way: `functions`, then `nodes`, then `conditions`.

The nodes:

| Node | Meaning |
|---|---|
| `FieldMeta` | a field of the record being tested; the field's metadata is the leaf itself |
| `BinOp(op, left, right)` | arithmetic on fields and numbers |
| `Call(fn, arg)` | a `Function` applied to a value; the `Function` holds its name, argument and result types, Python implementation and SQL |
| `Table(cls)`, `Filter(source, cond)` | all records of an entity, and those of a query that match a condition |
| `Sort(source, keys, reverse)`, `Slice(source, start, stop)` | a query sorted, and a slice of it; a view holds one query node and each method wraps it in another |
| `Compare(left, op, right)` | a value (a field, `BinOp` or `Call`) compared with a plain value, or with another value of the same record |
| `Match(field, kind, text)` | `startswith`, `endswith`, `contains` |
| `In(field, values)` | the field's value is one of the values, or the key of one of the records in a `Filter` |
| `And`, `Or`, `Not` | combining conditions |

A relation is membership, not navigation: `Order.customer.city == "Lisbon"` means "the order's `customer` is the key of one of the customers in Lisbon".

```python
In(Order.customer, Filter(Table(Customer), Compare(Customer.city, "==", "Lisbon")))
# where Order.customer and Customer.city stand for their FieldMeta
```

In Python this is `o.customer in {c.id for c in customers if c.city == "Lisbon"}`, and in SQL an `IN (SELECT ...)`.
`one_of(Order.status, values)` is the same node with a tuple of values.
Each relation in a chain such as `OrderLine.order.customer.city` adds one `In` around the condition on the last record.
Two fields can only be compared inside the same record, so `Order.customer.city == Order.customer.name` is one `Compare` inside one `In`.

### Compiling

A pure function turns a condition into `(sql, params)`.
Table and column names come only from the class metadata.
Values are always passed as parameters.

Relations become subqueries, so results are still whole records and never duplicated:

```python
Order.customer.city == "Lisbon"
# customer IN (SELECT id FROM customer WHERE city = ?)

OrderLine.order.customer.city == "Lisbon"
# "order" IN (SELECT id FROM "order" WHERE customer IN (SELECT id FROM customer WHERE city = ?))
```

Conditions that go through the same path are grouped into one subquery.
A path that ends on the target's key needs no subquery: `Order.customer.id` is the `customer` column.

`startswith("A")` compiles to `substr(name, 1, 1) = ?`, because SQLite's `LIKE` ignores case.
`contains` uses `instr`.

## Reading

`db[Customer]` is a `RecordSet`: a lazy collection of all customers.
The keys of `db` are the entity classes passed to `inlay.open`.
Any other class raises `KeyError`, so a db only has the tables it was opened with.
`__getitem__` is generic (`def __getitem__[T](self, cls: type[T]) -> RecordSet[T]`), so type checkers see `db[Customer]` as a `RecordSet[Customer]`.
`db` is not typed as a `Mapping`, because `Mapping[type, RecordSet]` loses the link between the class and its record set.
Only `db[T]` is supported; `in`, iteration and `len` on `db` can be added if needed.

`filter`, `sorted` and slicing return a `RecordView`, a new lazy collection that can only be read.
Record sets and views are immutable values.
No SQL runs until they are used.

The record set and views share the read operations below (`coll` is either).
Deleting by key or condition is only on the record set (see writing), so it is always clear what a delete covers.

| Operation | Result | SQL |
|---|---|---|
| `for c in coll` | each record | `SELECT ... WHERE ... ORDER BY ... LIMIT ...` |
| `coll.filter(*conds)` | new collection | adds to `WHERE` |
| `coll.sorted(key=..., reverse=False)` | new collection | `ORDER BY` |
| `coll[:10]`, `coll[20:30]` | new collection | `LIMIT` and `OFFSET` |
| `coll.get(key)` | `T \| None` | `WHERE id = ?` |
| `len(coll)` | `int` | `COUNT(*)` |
| `coll.sum(value)` | number | `SUM(value)`, 0 when empty |
| `coll.min(value, default=...)` | value | `MIN(value)` |
| `coll.max(value, default=...)` | value | `MAX(value)` |
| `obj in coll` | `bool` | an equal row exists |

Details:

- **Iterating runs the query again each time**, so it sees current data.
  `tuple(coll)` gives a snapshot.
- **Rows are read lazily**, one batch at a time, so big results do not have to fit in memory.
- **Writing to a record set while iterating over it raises `RuntimeError`**, like changing a `dict` during iteration.
  SQLite does not define what an open `SELECT` returns after its table changes on the same connection: rows can be skipped or seen twice.
  - Only the tables an iteration reads count: the collection's table and any table in its filter's subqueries.
    Adding orders while looping over customers is fine.
  - `db` keeps a count of open iterations per class.
    An iteration adds to it when it starts and removes from it in a `finally` when it ends.
    Every write checks the count first and raises `RuntimeError: Order changed during iteration`.
  - `break` closes the iteration right away, because CPython closes a generator as soon as nothing refers to it.
    An iterator you hold yourself (`it = iter(coll)`) keeps its tables open until it is finished or deleted.
  - To change rows while looping over them, take a snapshot first: `for o in tuple(db[Order].filter(...)):`.
- **`sorted`** copies the built-in `sorted(iterable, key=, reverse=)`.
  `key` is a value (`Order.total`, `Order.total - Order.discount`, `to_month(Order.placed)`) or a tuple of values, like a key function that returns a tuple.
  `list.sort()` is left out because it changes the list in place, and collections are immutable.
  The built-in `sorted(coll, key=...)` still works, but it sorts in Python.
  `reverse` applies to every value in `key`.
  The key of the record is the last sort field, so records that tie always come in the same order and slices of a sorted view never repeat or skip a record.
  Sorting twice works like the built-in: the last sort is the main one and the earlier ones break ties.
  Only fields of the class itself can be used, because sorting by a related field would need a join.
- **Slicing** takes `start` and `stop` only, with no step and no negative numbers.
  Without `sorted`, the order is whatever SQLite returns.
  A slice is applied after the conditions and the order, so `filter`, `sorted` and slicing on a sliced view work on the slice, as they would on a list: `coll[:10].filter(...)` filters those ten.
  In SQL, the sliced view becomes a derived table: `SELECT ... FROM (SELECT ... LIMIT 10) WHERE ...`.
- **`in`** follows `set`: `obj in coll` checks for a record with all fields equal, not only the same key.
  Use `coll.get(key) is not None` to check a key.
- **`get`** on a filtered collection returns `None` if the record exists but does not match the filter.
- **`min` and `max`** copy the built-ins: on an empty collection they raise `ValueError` unless `default` is given.
- **`len`, `sum`, `min` and `max`** work on a sliced view too: they run over the slice.
- **`len(coll)` also runs when a collection is passed to `list` or to the built-in `sorted`, or tested with `if coll:`.**
  `list` asks for the length first, as a hint for how much memory to reserve, and `if coll:` asks for it to decide.
  That is one extra `COUNT(*)` query.
  `for`, `tuple` and `set` do not ask.

## Writing

Writes that take records are methods on `db`.
The class comes from each record, so one call can mix classes.
Writes that take keys or conditions are methods on the record set, which says the class.

| Operation | Meaning | SQL |
|---|---|---|
| `db.add(*objs)` | insert, fails if a key exists | `INSERT` |
| `db.update(*objs)` | insert or replace by key | `INSERT ... ON CONFLICT(id) DO UPDATE` |
| `db.remove(*objs)` | delete equal records, fails if one is not stored | `DELETE ... WHERE <all columns> = ?` |
| `db.discard(*objs)` | delete equal records, ignores ones not stored | `DELETE ... WHERE <all columns> = ?` |
| `db[T].delete(*keys)` | delete by key, fails if one is missing | `DELETE ... WHERE id IN (...)` |
| `db[T].clear(*conds)` | delete every row matching all conditions | `DELETE ... WHERE ...` |

- Names follow `set` (`add`, `remove`, `discard`, `clear`), and `update` means what it means for `dict`: replace by key.
  `delete` is the one method that takes keys, like `get`.
- `add` fails on an existing key, unlike `set.add`.
  Silently keeping the old version is the bug a separate insert is there to catch.
- `remove` and `discard` follow `set`: they delete a record only if the stored one is equal to it.
  If someone changed the record after you loaded it, `remove` raises `Missing` instead of deleting a version you never saw.
  Use `delete` to delete by key whatever the stored version is.
- Records are grouped by class, and each group is one `executemany`.
  Order inside a call does not matter, because foreign keys are checked at commit.
- Upsert uses `ON CONFLICT DO UPDATE`, not `INSERT OR REPLACE`, because `REPLACE` deletes the old row first.
- `db[T].clear()` with no conditions deletes every record, like `set.clear()`.
  Conditions are the same as in `filter`.
- There is no update by condition, because it would change rows without going through whole records.

## Transactions

- Each write call is atomic on its own: if one record fails, nothing from that call is written.
- `with db.transaction():` groups several calls.
  It starts with `BEGIN IMMEDIATE`, so the write lock is taken up front.
  It commits on success and rolls back on an exception.
- A nested `transaction()` runs as a savepoint inside the outer one.
  It commits together with the outer one, and if its block fails, only its own writes are undone.
- A write call inside a transaction is a savepoint too, so a call that fails and is caught leaves nothing behind.
- Reads that must agree with each other go inside a transaction.

## Opening the db

`inlay.open(path, entities)` follows `shelve.open` and `dbm.open`.
It is meant to be called through the module: `from inlay import open` would hide the built-in `open`.

- Opens the SQLite file and turns on `PRAGMA foreign_keys = ON` and `PRAGMA journal_mode = WAL`.
- Creates missing tables and indexes, all in one transaction, so a failure leaves the file unchanged.
- Checks that existing tables match the classes and raises `SchemaMismatch` if not.
  SQLite stores each `CREATE TABLE` statement as it was run, and inlay always creates tables itself, so the check compares the stored statement with the one inlay would generate now.
  A change in how inlay writes that statement would make older files fail the check, which is fine for now.
  `migrate` and `rename` change a stored table to match a class; see `notes/2026-11-13-migrations.md`.
- Index names are the table and field names joined by `__`, like `order__customer` or `customer__city__name`.
  Indexes are created with `IF NOT EXISTS`, so reopening is harmless.
  Indexes in the file that are no longer declared are left alone.
- Raises if a `Ref` points to a class that is not in `entities`.

`db.close()` closes the file.
`db` is also a context manager, so `with inlay.open(...) as db:` closes it at the end of the block.
Using `db` or any of its record sets or views after closing raises an error.

A `Db` works only in the thread that opened it, and other threads and processes open their own.

## Errors

- `AlreadyExists` from `add`.
- `Missing` from `remove` and `delete`.
- `BrokenRef` when a write would leave a `Ref` pointing to nothing, raised at commit.
- `SchemaMismatch` from `inlay.open`, listing every changed table.

All of them subclass one `StoreError`.
Raw `sqlite3` errors are not passed through for these cases.

## Joins and aggregates

A set-like store has no joins or aggregates as such.
You get whole records and combine them in Python:

```python
total = db[Order].filter(Order.customer == ana.id).sum(Order.total)

orders = tuple(db[Order].filter(Order.total > 100))
customers = {c.id: c for c in db[Customer].filter(one_of(Customer.id, {o.customer for o in orders}))}
pairs = [(o, customers[o.customer]) for o in orders]
```

Filtering through relations covers the most common reason for a join.
Following a relation one record at a time is fine with SQLite, because each query is a function call, not a network round trip.
Simple aggregates are methods on the collection: `len(coll)`, `coll.sum(value)`, `coll.min(value)` and `coll.max(value)`, where the value can be computed, as in `coll.sum(Order.total - Order.discount)`.
They run in SQLite and return one value, so no records are loaded.
They have to be methods because the built-ins `sum`, `min` and `max` just iterate and cannot be pushed down.
The built-ins still work on a collection, but they load every record.
`coll.aggregate_by(key, func, value)` gives one aggregate for each value of `key`, as a dict in key order, such as `invoices.aggregate_by(to_month(Invoice.at), sum, Invoice.total)`.
`key` is a value or a tuple of values, as in `sorted`, and keys with no records are left out, as in a `Counter`.
`func` is one of the built-ins `len`, `sum`, `min` and `max`, or an `Aggregate` from `functions` such as `avg`.
Each built-in stands for an `Aggregate` of inlay's, and an `Aggregate`, like a `Function`, holds its Python and its SQL.
Users write the built-ins they know, and import only what Python lacks; `avg` gives a float, as SQLite's `AVG` does.

## Modules

- `meta`: the metadata about each class (`EntityMeta`, `FieldMeta`) and `meta()` to read it.
- `entity`: the decorator, `key`, the field descriptors and `Ref`.
- `types`: Python type to SQLite type, and value conversion both ways.
- `nodes`: the condition tree, the functions that combine conditions, and the checks that walk the tree.
- `conditions`: the builder users write with: field references, `contains` and `one_of`.
- `functions`: `Function` and `Aggregate`, and the functions and aggregates that work on both plain values and fields, such as `to_month` and `avg`.
- `sql`: pure functions that each build one SQL statement or clause, such as one table or one index, from the metadata.
  Looping over entities, indexes and conditions happens in the code that calls it.
- `db`: `open`, the `Db` class, collections, transactions and errors.
  The only module that touches SQLite; its schema checks and planning are pure private functions.

## Out of scope for v1

- Optional fields and enums.
- Composite keys.
- Cascading deletes.
- Reverse relations, like `Customer.orders.any(Order.total > 100)` with `EXISTS`.
- Aggregates other than `len`, `sum`, `min`, `max` and `avg`, and conditions on groups (`HAVING`).
- Tracking which migrations have run, and migrations that change several classes in one step.
- An immutable db with history.
- Async, sharing a `Db` between threads, and other databases.

## Typing limits

Checked with mypy and pyright.

- A type checker sees `Order.total > 100` as a `bool`, so `filter` and the condition functions accept `Condition | bool`.
- `one_of(Order.total, ("a",))` is not flagged: the value type is inferred as `object`.
- `sorted(key=...)` takes a field, which a type checker sees as the field's type, so `key` is typed loosely.
  `sum`, `min` and `max` can use the column's type for their result: `coll.sum(Order.total)` is an `int`.

## Follow-ups

- **Check whether typing `Order.total` as the field's type pays off.**
  Type checkers see `Order.total` as an `int` and `Order.customer` as a `type[Customer]`, but at runtime both are an `Expr`.
  This costs a lot of code:
  - the `_Field` descriptor and the `Ref` marker class,
  - casts in `contains`, `one_of` and `negate`, and the `Condition | bool` signatures,
  - `# type: ignore[override]` on `__eq__` and `__ne__`,
  - the name-mangled slots and `__getattr__` on `Expr`.
  It also lies to the reader: nothing in the types says that a class-level field is not a value.
  When the read side is done, compare it with explicit field objects, such as a separate accessor typed `Field[int]`, and keep whichever is simpler overall.
- **Compile conditions in two steps if they need optimizing.**
  `condition_sql` goes from the condition tree straight to SQL text, and it builds one subquery for each condition on a relation.
  These two optimizations from the Compiling section are not done yet:
  - conditions that go through the same path share one subquery,
  - a path that ends on the target's key (`Order.customer.id`) becomes the `customer` column.
  Both give the same results as now, and both are awkward on strings.
  Relations are `In` nodes in the tree, so both are tree rewrites before rendering: merge sibling `In`s on the same field, and replace an `In` whose inner condition only tests the target's key.
- **Not passing entities to `inlay.open`.**
  Listing every entity is clunky.
  A global registry filled by `@entity` would put every entity in the process into every db (including ones from tests or other modules), depend on import order, and hide global state.
  An alternative is to set up an entity the first time it is used (`db[T]` or a write), together with the entities its `Ref` fields point to.
  The cost is that `SchemaMismatch` shows up on first use instead of at `open`, and tables may be created inside a transaction.
- **Open items from the review of 2026-11-11.**
